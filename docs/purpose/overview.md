# 원본 DB ↔ 벡터 인덱스 간극 측정 (YBIG DE 컨퍼)

## 대목적
P0: RAG·추천 시스템을 만드는 엔지니어가 원본 DB와 벡터 인덱스 사이의 간극(옛 버전이 검색되는 현상)이 언제·왜·얼마나 생기는지 알 수 있도록, 위키 편집과 커머스 상태 변경을 CDC 파이프라인으로 리플레이해 간극을 측정하고, 반영 주기에 따른 시간 간극과 HNSW 인덱스의 업데이트 처리 방식(꺼두기·지웠다 다시 넣기·재구축)에 따른 구조 간극이 데이터 성격(본문이 바뀌는 위키 / 상태가 꺼졌다 켜지는 커머스)에 따라 어떻게 다른지 보여준다.

- 제약: 5인 1조, 마감 2026-12-23 (YBIG DE 컨퍼 발표). DE 트랙이라 Postgres → Debezium → Kafka 경로를 실제로 쓴다 (D-02). 실행 환경은 로컬 Docker compose. 임베딩은 bge-m3로 사전 계산해 R2에 둔다 (D-03). 벡터 저장소는 FAISS (D-01). 실험 2의 지웠다 다시 넣기만 hnswlib를 쓴다 (D-07). 위키 수집기(Oracle VM)는 R2에 적재 중.
- 비목표: FAISS C++ 소스 수정, 챗봇 답변(LLM 생성) 품질 평가, 임베딩 모델 비교, Qdrant·pgvector 비교, 범용 벡터DB 제품화.
- 성공 기준: 실험 0·1·2의 그래프가 같은 리플레이 입력에서 명령 하나로 재현되고, 같은 설정 2회 실행 시 결과 차이가 허용 폭 이내다 (잠정: 허용 폭은 M0 실측 후 결정).

## 목적 계층
- P1 간극이 실제로 생긴다는 것을 측정으로 보인다 (실험 0) — 이유: 간극이 측정 가능한 크기로 존재해야 P2·P3가 의미를 가진다 / 달성 결과: 편집 후 경과 시간별 stale 비율 곡선 [확정]
  - P1.1 위키 편집을 원래 시간 순서로 Postgres에 재생 — 이유: 실시간 편집 흐름을 반복 가능하게 재현 / 달성 결과: 배속 조절 가능한 리플레이 [확정]
  - P1.2 Postgres 변경을 FAISS까지 반영하는 경로 — 이유: 원본(리더)과 벡터 인덱스(팔로워)가 분리된 구조가 간극의 원인 / 달성 결과: Debezium → Kafka → 임베딩 워커 → FAISS 경로 [확정]
  - P1.3 같은 시점 Postgres 최신과 FAISS 결과를 비교해 채점 — 이유: 정답 기준(Postgres) 대비 판정 / 달성 결과: 정상·stale·누락 판정 로그 [확정]
- P2 시간 간극: 언제 반영하나 (실험 1, 위키). 반영 주기(즉시 / 묶어서)와 리플레이 배속을 바꿔 가며 stale 비율 변화를 보고, 어느 구간에서 시간이 걸리는지 확인한다 — 이유: 간극이 어느 구간(Debezium·Kafka 대기·임베딩·FAISS 반영)에서 생기고 반영 주기에 따라 얼마나 달라지는지 알아야 반영 시점을 정할 수 있다 / 달성 결과: 반영 주기 × 배속 조건별 stale 곡선 비교, 구간별 지연 분해 [확정]
- P3 구조 간극: 반영이 끝난 뒤에도 인덱스 구조 때문에 검색이 나빠지나 (실험 2, 위키 + 커머스) — 이유: 반영을 해도 인덱스 구조 때문에 생기는 간극이 따로 있다. 업데이트가 일어나는 방식이 정반대인 두 데이터를 같은 세 방식으로 처리해야 한 데이터에서만 맞는 결론을 피하고, 데이터 성격에 따라 맞는 처리 방식이 다르다는 것을 보일 수 있다 / 달성 결과: 가로축은 시간이 아니라 누적 업데이트 수. 인덱스는 HNSW로 고정하고, 정답(recall 기준)은 같은 시점·같은 질의의 Flat 전수조사. 처리 방식 3가지(꺼두기: 옛 노드는 두고 검색 결과에서만 거름 / 지웠다 다시 넣기: 옛 노드를 지우고 새 노드를 넣음 / 재구축: 업데이트가 일정량 쌓이면 HNSW를 통째로 새로 만듦)별 recall@10, 검색 지연 p95(질의 100개), 구버전 혼입률(top-10에 옛 리비전이나 품절 상품이 섞이는 비율), 비용(쓰기·삭제 횟수, 재구축 시간) 그래프 [확정]
  - P3.1 위키: 본문이 바뀌는 데이터. 문서를 고치면 벡터 자체가 바뀌고 옛 벡터는 다시 쓰이지 않아 버려진 노드가 계속 쌓인다 — 이유: 꺼두기에서 꺼둔 노드가 쌓이면 recall·검색 속도가 얼마나 떨어지는지, 지웠다 다시 넣기가 그래프를 덜 망가뜨리는 대신 쓰기 비용은 얼마인지, 재구축은 언제가 적당한지 본다 / 달성 결과: 세 방식의 누적 업데이트 대비 지표 그래프, 꺼두기 recall 저하 곡선으로 정한 재구축 기준. 데이터는 kowiki 수집분, 되돌림 표본이 부족하면 enwiki MediaWiki History로 보완(본문이 필요한 것은 샘플 문서만 API로) [확정]
  - P3.2 커머스(Retailrocket): 상태가 꺼졌다 켜지는 데이터. 품절돼도 상품 벡터는 그대로이고 재입고되면 다시 쓰여, 같은 노드가 꺼졌다 켜지기를 반복한다 — 이유: 꺼두기가 동시 품절이 많아져도 버티는지, 지웠다 다시 넣기에서 같은 벡터를 매번 지웠다 넣는 낭비가 얼마인지, 주 단위 품절 상태마다 재구축하면 비용 대비 이득이 있는지 본다 / 달성 결과: 세 방식의 누적 업데이트 대비 지표 그래프. 상품 벡터는 item2vec(같은 세션에서 같이 본 상품끼리 가깝게)으로 한 번 만들고 고정한다. 질의는 조회 이벤트(약 266만 건)를 추천 요청으로 보고, 그 사용자가 최근 본 상품 벡터의 평균으로 만든다. 결과는 품절 제외 상위 10개. 품절 기록이 주 단위 스냅샷이라 반영 타이밍 비교는 하지 않는다 (D-04) [확정]
  - P3.3 HNSW 위 정책(꺼진 비율 기준 재구축 트리거, 탐색 폭 자동 조절, 노션 Plus의 가역 우회 간선 등)으로 재구축 주기 개선 — 이유: 측정에서 끝나지 않고 개선안 제시 [미결: 2026-12-07에 착수 여부 결정 (D-05)]

## 미결·가정
- [가정] R2 위키 데이터에 편집 본문이 있다 → 확인 방법: T-01 (사용자)
- [가정] Postgres + Debezium + Kafka compose 구성이 반나절 안에 된다 → 확인 방법: T-03. 하루 초과 시 임시 폴링 (D-02)
- [가정] 간극이 측정 가능한 크기로 존재한다. 단, 간극의 상당 부분이 주입한 embed_ms에서 올 수 있다 (GR-03) → 확인 방법: T-07
- [가정] FAISS HNSW는 remove를 지원하지 않고, IDSelector로 걸러낸 노드도 탐색 중 경유한다 → 확인 방법: M1 초반 코드·문서 확인
- [가정] hnswlib로 노드를 지우고 다시 넣을 수 있다. 단, hnswlib의 삭제는 표시(mark_deleted)와 지운 자리 재사용(replace_deleted)이라, 간선까지 지우는 "지웠다 다시 넣기"와 다를 수 있다 → 확인 방법: M1 초반 코드·문서 확인 (D-07)
- [가정] 위키는 언제 재구축할지가 중요하고, 커머스는 지우지 말고 꺼두는 게 낫다 (노션 예상) → 확인 방법: P3.1·P3.2 그래프
- [미결] 실험 2의 세 방식을 모두 hnswlib로 할지, 꺼두기·재구축은 FAISS HNSW로 할지. 섞으면 라이브러리 차이가 방식 차이로 보일 수 있다 → 결정: 사용자(팀장), M1 초반 (D-07)
- [미결] 실험 2 위키(P3.1)의 질의 세트. 노션은 커머스 질의(조회 이벤트)만 정했다 → 결정: 사용자(팀장), M1 초반
- [미결] 노션의 "실험 2에서 확인할 지표" 설명에는 IVF·HNSW 비교가 남아 있으나, 실험 2 본문(HNSW 고정)을 따라 IVF는 뺐다. IVF를 비교에 넣을지 → 결정: 사용자(팀장)
- [미결] P3.3 착수 여부 → 결정: 사용자(팀장), 2026-12-07
- [미결] 노션 Plus 아이디어(품절 시 우회선 추가, 재입고 시 해당 우회선만 제거)를 P3.3에 넣을지 → 결정: P3.3 착수 시. 플로이드-워셜(O(n³) 전체 쌍 최단거리)은 ANN 그래프에 맞지 않음
