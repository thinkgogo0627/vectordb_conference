## D-01 벡터 저장소는 FAISS 라이브러리를 감싼 서비스로 한다 (2026-11-16)
- 관련: P1.2, P3, T-05
- 이유·근거: 버전 교체·삭제 표시·재구축을 직접 구현해야 간극의 원인을 측정할 수 있다. Qdrant는 이를 내부에서 처리해 가린다. FAISS 내부 알고리즘(Flat·IVF·HNSW) 탐구와 같은 자리에서 연결된다.
- 검토한 대안: Qdrant (구현 비용 낮음, 내부 동작이 가려짐), Qdrant + FAISS 병행 (5주 범위에 과함)
- 영향: 검색 서비스·교체 로직을 직접 구현하는 비용이 생긴다. Qdrant·pgvector 비교는 제외(P4).
- 재검토 조건: FAISS 서비스 구현이 M0 일정을 크게 넘길 때

## D-03 임베딩은 bge-m3로 사전 계산해 R2에 두고, 워커는 실측 embed_ms만큼 대기 후 반영한다 (2026-11-16)
- 관련: P1.2, P2, T-02, T-05
- 이유·근거: bge-m3를 실시간으로 CPU에서 돌리면 반복 실험이 느리다. 대기 시간을 넣지 않으면 지연이 실제보다 짧게 나온다.
- 검토한 대안: 워커가 실시간 임베딩 (현실적이지만 반복성·속도 낮음)
- 영향: 간극의 일부가 주입한 embed_ms에서 온다. 해석 시 구분한다 (GR-03).
- 재검토 조건: 실시간 임베딩 비용이 문제 되지 않는 환경을 확보할 때

## D-04 커머스(Retailrocket)는 실험 2(구조 간극)에만 쓴다 (2026-11-16)
- 관련: P3.2, P5
- 이유·근거: 품절 기록이 주 단위 스냅샷(일요일 03시 UTC)이라 분·초 단위 반영 타이밍 비교가 불가능하다. 누적 업데이트 대비 인덱스 지표는 시간 해상도와 무관하다.
- 검토한 대안: 커머스 보류 (사용자 반대), 다른 커머스 데이터 탐색 (실패 위험 큼)
- 영향: 커머스 반영 타이밍 실험 제외. 상품 벡터는 item2vec으로 만든다.
- 재검토 조건: 분 단위 상태 변경 기록이 있는 데이터를 확보할 때

## D-06 실험 0의 간극 측정 정의 (2026-11-16)
- 관련: P1.3, T-06, T-07
- 이유·근거: 질의 세트 없이 원본과 인덱스의 일치를 바로 잴 수 있다. 실험 1에서 같은 곡선을 조건별로 겹쳐 비교할 수 있다.
- 내용: 방금 편집된 청크의 최신 리비전 임베딩으로 질의해 top-1이 최신 리비전이면 정상, 옛 리비전이면 stale, 해당 청크가 없으면 누락. 그래프는 x축 편집 후 경과 시간(초), y축 아직 stale인 편집 비율.
- 검토한 대안: 문서 제목·바뀐 문장으로 만든 질의 세트 (현실적이나 구축 비용), 리플레이 시간축 그래프 (몰림 시점은 보이나 간극 길이를 읽기 어려움)
- 영향: 실험 0은 실제 사용자 질의 품질이 아니라 인덱스 동기화 상태를 잰다. 실제 질의는 실험 2 recall에서 다룬다.
- 재검토 조건: 실험 1·2에서 이 정의가 조건 간 차이를 드러내지 못할 때
